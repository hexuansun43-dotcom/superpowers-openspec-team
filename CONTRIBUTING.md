# Contributing

Thanks for contributing to `superpowers-openspec-team-skills`.

This repository contains three related layers:

- `skills/`: maintainer-facing source workflow definitions
- `dist/`: tool-adapted distributable bundles (generated by `sot build`)
- `src/`: CLI source code (TypeScript)

Keep `skills/` and `dist/` functionally aligned. `dist/` is regenerated by `sot build` -- do not edit it directly.

## Before You Start

1. Read [README.md](README.md).
2. If your change affects CLI behavior, install and run the CLI locally: `npm run build && node bin/sot.js <command>`.

## What Kinds of Contributions Are Welcome

- workflow improvements in `skills/`
- CLI bug fixes or new commands in `src/`
- adapter improvements or new adapters in `src/core/adapters/`
- documentation improvements
- test coverage improvements

## Contribution Rules

### 1. Keep explicit activation intact

Do not change the repository so installed workflows become default background behavior unless the change is explicitly intended and discussed.

### 2. Preserve source vs bundle separation

If you change `skills/`, run `sot build` to regenerate `dist/` and verify that bundles remain consistent.

### 3. Prefer small, reviewable changes

Keep pull requests focused. Avoid mixing:

- CLI changes
- workflow behavior changes
- large documentation rewrites
- unrelated formatting

### 4. Keep docs aligned when behavior changes

If you change behavior, update the relevant documentation, usually one or more of:

- [README.md](README.md) / [README.cn.md](README.cn.md)
- [CHANGELOG.md](CHANGELOG.md)

### 5. Do not silently widen trust or automation boundaries

Be careful with changes that:

- auto-enable workflows
- auto-write durable memory
- auto-promote learning candidates
- change installation targets
- expand script or CLI side effects

## Local Validation

Run the checks that match your change.

### CLI and build changes

```bash
npm run build          # compile TypeScript
npx tsc --noEmit       # type check without emitting
npm test               # run vitest suite
sot validate .         # validate installation integrity
```

### Workflow or bundle changes

```bash
sot build              # rebuild dist/ from skills/
sot validate .         # check installation markers and checksums
sot list               # verify skills are parsed correctly
```

### Memory template changes

```bash
sot init /tmp/test-project --with-memory --dry-run
```

### Installer or integration changes

Legacy scripts still exist under `scripts/`. If you change them, validate in a real POSIX shell when possible.

```bash
sh scripts/install-codex.sh --bundle openspec-superpowers --codex-home /tmp/codex-test --dry-run
```

## Pull Request Checklist

Before opening a PR, confirm:

- the change is scoped and reviewable
- affected docs were updated
- `npm test` passes
- `npx tsc --noEmit` passes (for CLI changes)
- `sot build` produces consistent output (for workflow changes)
- behavior still matches the explicit opt-in model

## Documentation Expectations

When introducing a new user-facing capability, prefer to document:

- what it does
- when it runs
- how it is triggered
- whether it is explicit or automatic
- how to verify it

## Questions

If a change has unclear product, workflow, or licensing implications, open an issue or draft PR first instead of guessing.
